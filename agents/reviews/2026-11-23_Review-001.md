### #1 [P2] The publishing template evaluates tag names as Bash source [Deferred]

- **Status** Deferred
- **Location** `.agents/skills/nuget-trusted-publishing/references/publish-workflow.md:33-40` and `.claude/skills/nuget-trusted-publishing/references/publish-workflow.md:33-40`
- **Problem and trigger** When a repository adopts the template, every pushed tag matching `v*` reaches version validation. The step substitutes the tag-derived output into two inline Bash commands before Bash parses them.
- **Impact** A tag creator who can trigger the publish job can alter command execution in a job configured with `id-token: write`. Even an unintended malformed tag can break the version step. The checked-in release workflow uses an environment variable for its release input.
- **Evidence** `GITHUB_REF_NAME` first becomes a step output. The two expressions in the next step turn that output into script text before the comparison runs. The tag filter checks the prefix only. [GitHub Actions script injection guidance](https://docs.github.com/en/actions/concepts/security/script-injections)
- **Suggested resolution** Read the tag from `GITHUB_REF_NAME` in the validation step or pass the version through an environment variable. Validate its form before using it as a version, and reference only quoted shell variables in the script. [GitHub Actions guidance on environment variables](https://docs.github.com/en/actions/reference/security/secure-use#use-an-intermediate-environment-variable)
- **Verification** In a local workflow harness without credentials, a well-formed tag reaches the project version comparison and an invalid tag is rejected without changing the command the shell parses.
- **Disposition** Deferred on 2026-11-23 by the repository owner. The finding applies to agent skills under `.agents/skills/` and `.claude/skills/`, many of which were copied from the dotnet skills repository and may be removed from the brows-* repositories if they prove unhelpful or contradictory.

### #2 [P2] The release example pushes every local tag [Deferred]

- **Verification** With two local version tags and an empty local test remote, run a dry-run push of the documented command and confirm that it lists just the intended tag.

### #4 [P3] The README overstates when .NET Framework needs native copy targets [Resolved]

- **Status** Resolved
- **Location** `README.md:215-219`
- **Problem and trigger** The README says .NET Framework consumers depend exclusively on the package targets to copy the native files. An SDK-style .NET Framework consumer with an explicit RID also receives the RID's native files from the SDK.
- **Impact** Developers inspecting a .NET Framework RID publish can mistake the additional root assets for a packaging fault or expect the documented layout to contain only the architecture subdirectories.
- **Evidence** A clean `net48` WPF publish with `-r win-x64` produced five x64 files beside the app plus both five-file sets under `runtimes/`. The SDK documents native asset selection for these consumers. [Native files in .NET packages](https://learn.microsoft.com/en-us/nuget/create-packages/native-files-in-net-packages#sdk-style-projects-targeting-net-framework)
- **Suggested resolution** Explain that the targets provide both native architectures for portable .NET Framework consumers and that an SDK-style RID-specific build can also copy its selected assets to the root.
- **Verification** Compare fresh portable and `win-x64` `net48` outputs with the revised description.
- **Resolution** `README.md:214-223` now says the `buildTransitive` rules apply only to .NET Framework consumers and copy both architectures under `runtimes/`, and that an SDK-style .NET Framework project with a runtime identifier, explicit or inferred from an x64 `PlatformTarget`, also receives that architecture's files beside the application, with the loader preferring the `runtimes/` copies (`source/Brows.TTY/Interop/NativeLibraries.cs:63-66`).
- **Validation** Fresh `net48` copies of the WPF consumer against `0.1.1-alpha` with .NET SDK 10.0.404: a portable AnyCPU build (inferred RID `win-x86`, which has no assets) produced only the two five-file `runtimes/` sets; a `PlatformTarget=x64` build (inferred RID `win-x64`) and a `win-x64` publish each produced five root files plus both `runtimes/` sets. These match the revised description. Documentation change only; no automated test applies.

### #9 [P3] The pooled buffer recipe changes what callers can read [Deferred]

- **Status** Deferred
- **Location** `.agents/skills/analyzing-dotnet-performance/references/critical-patterns.md:52-65` and `.claude/skills/analyzing-dotnet-performance/references/critical-patterns.md:52-65`
- **Problem and trigger** The example replaces a fresh, zero-filled 4,096-byte array with a rented buffer and gives the whole array to `Process`. The recipe also returns the buffer only on the success path.
- **Impact** A caller reading the entire array can process stale data or the wrong length. Processing failures prevent buffer reuse.
- **Evidence** The API contract allows larger arrays and previous contents. The code passes the array without a logical length or initialization, and an exception skips the call to `Return`. [ArrayPool.Rent contract](https://learn.microsoft.com/en-us/dotnet/api/system.buffers.arraypool-1.rent)
- **Suggested resolution** Pass only the logical slice, initialize any bytes the consumer reads before writing, and return the buffer in `finally`. Choose clearing based on the data's lifetime requirements.
- **Verification** Use a pool that supplies a larger dirty buffer and a processor that can throw. Confirm the processor sees the intended bytes and the rental is returned in both paths.
- **Disposition** Deferred on 2026-11-23 by the repository owner.
