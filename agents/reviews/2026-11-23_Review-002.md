## Summary

## Findings

### #1 [P2] Preserve xterm modifyOtherKeys input for legacy VT applications [Resolved]

- **Status** Resolved.
- **Location** `native/bridge/brows_session.c:344-350` and `source/Brows.TTY.Win32/Win32/TerminalSession.cs:44-47`
- **Problem and trigger** An application enables `ENABLE_VIRTUAL_TERMINAL_INPUT` and requests xterm `modifyOtherKeys` mode 2 with `CSI > 4 ; 2 m`. With mode 9001 active and Kitty flags clear, the new path sends Win32 records and bypasses Ghostty's encoder. The bundled ConPTY decodes those records and emits its own VT bytes. [xterm control sequences](https://invisible-island.net/xterm/ctlseqs/ctlseqs.html) · [Bundled ConPTY input dispatch](https://github.com/microsoft/terminal/blob/v1.25.2733.0/src/terminal/parser/InputStateMachineEngine.cpp#L383)
- **Impact** Shift+Enter and Ctrl+Enter lose their modifier identity in the application's byte stream. Shift+Tab also changes encoding, which can break an application's bindings for the requested protocol.
- **Evidence** A scratch copy of `tests/native/KeyEcho.c` requested only xterm mode 2 in place of Kitty flags. Through the same pinned ConPTY, invoking the unchanged Ghostty encoder used by baseline `TerminalSession.Key` produced `CSI 27;2;13~` for Shift+Enter, `CSI 27;5;13~` for Ctrl+Enter, and `CSI 27;2;9~` for Shift+Tab. Invoking target `TerminalSession.Key` produced CR, LF, and `CSI Z` respectively. The child reported these bytes before an explicit end marker.
- **Suggested resolution** Honor the effective Ghostty keyboard protocol when selecting the input format. Keep Ghostty encoding for an explicit `modifyOtherKeys` mode 2 request as well as for Kitty flags.
- **Verification** Add a raw VT input case requesting xterm mode 2. Verify the exact three sequences above and retain the existing classic console and Kitty cases.
- **Resolution** With mode 9001 active and Kitty flags clear, the native bridge encodes a synthetic Shift+Tab under the terminal lock. Only a successful `CSI Z` selects Win32 records. The probe writes to a private buffer.
- **Regression evidence** `ModifiedKeys_FollowModifyOtherKeysModeChangesInTheSameSession` reproduced CR, LF, and `CSI Z` before the fix. After the fix, the helper received exactly the three requested sequences, cleared mode 2, and received CR for the next Shift+Enter. The classic console and Kitty cases also passed on x64.

### #2 [P2] Preserve keypad identity and pair releases by physical key [Deferred]

- **Status** Deferred.
- **Location** `source/Brows.TTY.Win32/Win32/PlatformInvoke/WindowsKeyTranslator.cs:93-102` and `source/Brows.TTY.Win32/Win32/TerminalSession.cs:29-40`
- **Problem and trigger** The new record path reconstructs scan codes and `ENHANCED_KEY` from the virtual key. Both Enter keys use `VK_RETURN`, and with Num Lock off, both Up keys use `VK_UP`. The originating Windows message distinguishes each pair with its extended-key bit. WPF carries that bit internally, but `source/Brows.TTY.Windows/Windows/Controls/TerminalEmulator.cs:1296` and `source/Brows.TTY.Windows/Windows/Controls/TerminalEmulator.cs:1349-1355` route and track the logical key. [Windows keyboard input flags](https://learn.microsoft.com/en-us/windows/win32/inputdev/about-keyboard-input#extended-key-flag) · [WPF message translation](https://github.com/dotnet/wpf/blob/v10.0.0/src/Microsoft.DotNet.Wpf/src/PresentationCore/System/Windows/InterOp/HwndKeyboardInputProvider.cs#L468-L488)
- **Impact** A classic console application cannot bind the keypad Enter or keypad navigation variants separately. If both Enter keys are held together, the first release clears the shared entry and the second release is lost.
- **Evidence** A WPF probe raised preview key events with the scan code and extended bit set as Windows supplies them, then read the records from `key-records.exe` over ConPTY. Both Enter variants arrived as `VK_RETURN` with `ENHANCED_KEY` clear. With Num Lock off, both Up variants arrived as `VK_UP` with `ENHANCED_KEY` set. Two overlapping Enter presses delivered two key-down records and one key-up record.
- **Suggested resolution** Capture the scan code and extended bit from the originating Windows keyboard message when available. Carry that identity through WPF's pending-text and forwarded-key tracking into record generation. Use the layout-derived mapping for synthetic input that lacks hardware metadata.
- **Verification** Check both Enter and Up pairs with a classic console reader. Assert `ENHANCED_KEY` on keypad Enter and dedicated Up, clear it on main Enter and keypad Up, and verify a separate key-up for each overlapping press.
- **Disposition** Deferred on 2026-11-23 by the repository owner. The keypad identity loss predates this change. At baseline `cf69183`, `bt_win32_key` maps `VK_RETURN` to Ghostty's Enter for both Enter keys, Ghostty encodes it as CR, and ConPTY delivers a plain `VK_RETURN` without `ENHANCED_KEY`. Baseline `ESC [ A` already arrives as `VK_UP` with `ENHANCED_KEY` set for either Up key; `UpArrow_ReachesConsoleApplicationAsEnhancedKey` passed with the win32 record path temporarily disabled. The lost overlapping release also predates this change: the control tracks forwarded keys by WPF `Key` (`source/Brows.TTY.Windows/Windows/Controls/TerminalEmulator.cs:71`) and returns before forwarding when `_forwardedKeys.Remove(key)` fails (`TerminalEmulator.cs:1349-1351`), so Kitty applications lost the second Enter release at baseline as well. The only new consequence is an unbalanced down, down, up sequence for classic console readers, where baseline CR input produced a synthesized down and up per press. Correcting both requires capturing the scan code and extended-key bit from the originating Windows message, which WPF keeps internal, for example through `ComponentDispatcher.ThreadFilterMessage`, and carrying that identity through the control's pending-text and forwarded-key tracking. That moderate change benefits only applications that bind keypad variants separately or track Enter key-up events, so it is deferred as a low-priority improvement rather than fixed in this branch.
